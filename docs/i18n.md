# Shop-facing language (i18n)

The app renders its own chrome — page titles, nav, labels, buttons,
descriptive prose, toast/error messages — in **one language per
deployment**, chosen by the shop. This is *shop-facing*: a Taiwan shop
runs the whole app in Traditional Chinese, a Japanese shop in Japanese.
It is **not** per-user and **not** switchable at runtime. User-generated
content — event titles, notes, and the shop's own catalog rows
(`prices`, `rooms`, `addons`, `travel_destinations`) — is never
translated.

## How selection works

The language is a build-time constant, read from the config seam exactly
like `locale.currency`:

```ts
// fundive.config.ts
locale: {
  timezone: 'Asia/Taipei',
  currency: 'TWD',
  currencyLabel: 'NTD',
  language: 'en',   // 'en' | 'zh-TW' | 'ja'
  units: 'metric',  // 'metric' | 'imperial' — see below
},
```

`locale.units` is a separate field on purpose. It picks which side of the
height/weight toggle a diver sees first (`src/lib/units.ts`), and it is not
derivable from `language`: this shop renders in English from Taiwan, where
everyone is metric, so inferring imperial from `'en'` would have been wrong.
Storage stays metric — `profiles.height_cm` / `profiles.weight_kg` — whichever
way the toggle is set, and each diver's choice is remembered per browser.

Because it's a constant, there is **no React context or provider**. The
catalog is resolved once at module load in `src/i18n/index.ts`:

```ts
import { t } from '../i18n'

<h1>{t.dashboard.title}</h1>
<span>{t.shell.pending(count)}</span>
```

`t` is a plain object — the message catalog for the configured language.

## The catalogs

```
src/i18n/
  index.ts              # resolves `t` from siteConfig.locale.language
  messages/
    en.ts               # source of truth; its type IS the contract
    zh-TW.ts            # const zhTW: Messages = { … }
    ja.ts               # const ja:   Messages = { … }
  messages.test.ts      # runtime shape-parity backstop
```

`en.ts` exports the catalog **and** its inferred type:
`export type Messages = typeof en`. Every other catalog is annotated
`const zhTW: Messages = { … }`, so a **missing or misnamed key fails the
TypeScript build** — English is the schema. `messages.test.ts` re-checks
the same shape at runtime and confirms the configured language resolves.

Rules for catalog files:

- **Pure data / plain functions only.** No imports from `src/config` or
  React. This keeps a catalog portable to the Deno edge-function runtime
  (see "Not yet covered" below).
- **No `as const`** on the catalog object — values must widen to `string`
  so a translation can supply a different literal for the same key.
- **Interpolation is a function.** A string that needs a runtime value is
  a function; its parameter names and types propagate to every
  translation through the shared `Messages` type:

  ```ts
  // en.ts
  greeting: (name: string) => `Hi ${name}`,
  // zh-TW.ts  — signature is enforced
  greeting: (name: string) => `${name} 您好`,
  ```

Catalogs are namespaced by area (`nav`, `common`, `shell`, `dashboard`,
`register`, `admin.*`, …). Keep a key where its text is used.

## Adding a string

1. Add it to `src/i18n/messages/en.ts` under the right namespace.
2. Add the **same key** to `zh-TW.ts` and `ja.ts` (the build fails until
   you do).
3. Replace the inline literal in the component with `t.namespace.key`.

Module-scope constants (e.g. a nav array) can reference `t` directly —
`t` is resolved at import time, before those constants initialize.

## Adding a language

1. Extend `SupportedLanguage` in `src/config/site.ts`.
2. Extend the zod enum in `src/config/site.schema.ts`.
3. Add `src/i18n/messages/<tag>.ts` (`const xx: Messages = { … }`) and
   register it in `src/i18n/index.ts`.
4. Bump `CONFIG_CONTRACT_VERSION` only if you also changed the config
   *shape* — adding an enum member does not require a bump.

> The `fundive.config.ts` value is type-checked against `SiteConfig`
> where the config is imported directly (this deployment repo), so the
> literal carries `as const` to narrow it to the union. Keep it.

## Keeping the two repos in sync

The `src/i18n` module and all three catalogs are **identical** in
`app-fundivers` and the upstream `fundive` repo — only the config
*wiring* differs (direct import vs the `virtual:fundive-config` plugin).
Port catalog changes to both.

## Translation quality

Shipped translations are a strong first pass. **Dive terminology and a
shop's local register deserve a native review before that shop flips
`language` away from `en` in production.** The English build is
unaffected while translations are reviewed.

## Emails and the PDF

The Deno edge-function runtime cannot load `src/config/site.ts` (it
resolves `../../fundive.config` extensionless), so it gets its own
selector: `supabase/functions/_shared/i18n.ts`, which imports
`fundive.config.ts` and the pure-data catalogs directly with explicit
`.ts` extensions. Same `t`, same catalogs, same single language.

Every email body and the registration PDF read from it. Two things stay
untranslated on purpose:

- **The partner's copy** of a package recommendation
  (`package-registration-email.ts`) — it goes to a third-party shop, not
  to this shop's diver.
- **Machine subject tokens** — `registration--`, `waitlist--`,
  `waitlist-offer--`, `manifest--`. Shops filter their inbox on these,
  so they are identifiers, not prose.

### CJK in the PDF

jsPDF's built-in helvetica is WinAnsi: it has no CJK glyphs and does not
fail on them, it silently emits mangled bytes. `pdf.ts` embeds
`pdf-cjk.ttf` and switches to it per string via `setFontFor`. Two rules
when you touch that file:

1. **Never call `doc.setFont("helvetica", …)` immediately before drawing
   text that could be CJK** — call `setFontFor(doc, text, style)`, which
   picks the embedded face when helvetica cannot encode `text`.
2. **The gate has to see the text.** `payloadNeedsCjkFont` only walks the
   registration payload; catalog labels and `identity.tagline` never
   travel in it. `catalogNeedsCjkFont` (in `pdf-fonts.ts`) covers those,
   invoking interpolating catalog values with a placeholder to reach
   their literal text. Without it a zh-TW deployment printing an
   all-Latin registration registers no font and mangles every label.

`pdf-font-coverage.test.ts` separately asserts the vendored font has a
glyph for every character the configured language's catalog prints —
Noto Sans TC lacks seven Japanese shinjitai, so a `ja` shop must swap the
font file.

### CSV exports

Every CSV builder leads with a UTF-8 BOM (`CSV_BOM`). Excel opens a
BOM-less UTF-8 CSV as the machine's ANSI codepage, which turns Chinese
diver names, event titles and notes into mojibake. Applies to the
dive-log export, the database backup and the accounting sheets.

### What the tests actually hold

- `pdf-render.test.ts` drives the real jsPDF renderer (through the
  `npm:jspdf@2.5.1` → `jspdf` alias in `vitest.config.ts`) and records the font
  every draw used. It fails if any string helvetica cannot encode reaches the
  page under helvetica — which is the only way to catch a stray
  `doc.setFont("helvetica", …)`, since that mistake throws nothing.
- `pdf-font-coverage.test.ts` declares which languages the vendored font can
  print (`SERVED`) and checks that against all three catalogs, not just the
  configured one. Noto Sans TC serves `en` and `zh-TW`; it lacks seven Japanese
  shinjitai and every Hangul syllable. Setting `locale.language` to a language
  outside `SERVED` fails the build.
- `outbound-copy.test.ts` scans the source of every module that composes an
  email, a PDF page or a file inside an export, and fails on a bare prose
  literal. Its `ALLOWED` list is the record of what stays English on purpose —
  currently only the partner-facing halves of the package recommendation and the
  trusted-partner introduction.

Glyph rendering **in the app** is not testable here and does not need to be: the
SPA embeds no font, so a CJK string is drawn with the viewer's own system fonts.
What can break there is layout, not encoding — CJK offers no space to wrap on —
and that needs a real browser, which neither repo has in CI.

## Not yet covered (separate surfaces)

- **Legal text** — `src/config/terms.tsx` / `src/config/waivers.ts` are
  hand-written JSX/prose. Machine-translating legal text is risky; keep
  English-only or use professionally-reviewed translations.
